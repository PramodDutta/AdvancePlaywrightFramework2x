Quality Gates in Seven Steps

Your suite is green, tsc is clean, ESLint says nothing, and the spec asserts nothing. Here is the smallest thing that catches it.

  • 7 steps
  • about 30 minutes
  • zero dependencies
  • Playwright + TypeScript

By Pramod Dutta, founder of The Testing Academy

1

The problem

A spec can pass everything you own and still check nothing.

It compiles. ESLint finds one unused parameter. The suite goes green. And it asserts nothing, so it reports green on a login page that is completely broken, as long as the button is still there to click.

A reviewer objects to this once, and then gets tired. That is the gap generated code walks through, and it widens with the volume an agent can produce.

Try it Open your own suite and grep for test( bodies with no expect. Count them.

2

Two tools, one line between them

ESLint owns what has a correct answer. A rule engine owns what needs your repo.

ToolOwnsCost
ESLintfloating promises, waitForTimeout, force: true, any~2.2s per file
Your engineis this used twice, does this comment add anything, does this spec use the fixture~0.14s, whole repo

"Does this spec go through the fixture layer?" has no universal answer. It depends on a module that exists in your repo. A general-purpose linter cannot ship that rule.

Four gates, each one question asked of every file:

ai-slop

Was this generated, skimmed, and shipped?

ponytail

Does anything else in the run already record this?

over-engineering

How many callers does this abstraction have?

framework-patterns

Is this still part of this framework?

One owner per rule. A hard wait is the most recognisable AI tell there is, and it does not go in your ai-slop pack, because playwright/no-wait-for-timeout already owns it. Two tools reporting the same finding teaches people to skim past both.

Try it Write down three things your team says in review that no linter could check. Those are your first rules.

3

Read the source safely

Never regex raw source. Mask the comments and strings first.

The same string, three times, and only one is a finding:

Walk the file once. Blank the comment bodies and string contents, keep every newline, so every offset still maps to its line.

Two traps. A / only starts a regex literal where a value is expected: get it wrong and const re = /\/\//; eats the rest of the file. And masking blanks the words a narrating comment is echoing, so a rule comparing a comment to its neighbour must read the raw line. Knowing which copy a rule needs is most of the skill.

Try it Write lex(), run it on your biggest page object, and check that no line number moved.

4

A rule is data, not code

Detectors are code. Rules are data. Adding one is a four-line change.

Write each rule as a function and fifty rules later nobody adds a rule. Write them as objects that name a detector, and anyone can.

why and fix are the product, not documentation. They print in your terminal, in the feedback the agent reads when its edit is blocked, and in the pull request comment. A rule whose why says "this is bad practice" gets waived by the first person who hits it.

Note required also accepts assertLoaded(). If your page objects assert, a rule that only knows expect will fire on your best specs.

Try it Add one rule for page.pause() in specs. Then put page.pause() in a comment and confirm it is not reported.

5

Teach it taste

The best rules come from a judgement your team already wrote down.

This framework keeps two copies of one API lifecycle test on purpose: 73 lines and 33 lines, same assertions, both green. Every cut answered one question.

Dividing by the smaller set means a short code line whose two identifiers both appear in a long comment scores 1.0. So it reported this, the single most useful line in the file:

The question is not "do these share words". It is does the comment add anything the code does not have. That makes the comment the denominator, always.

the same two comments, scored
// click the login button   over  el.click(loginButton)      1.00   reported
// No token argument: ...    over  bookingApi.updateBooking()  0.14   left alone

Validate a taste rule against something your team already agreed on. Here the 33-line spec reports clean and its 73-line twin reports exactly the cuts the README documents. Without a check like that, a taste rule is just your opinion with a CI job attached.

Try it Find the pair in your repo: the file everyone points at as good, and the one it replaced. Your rules must stay silent on the first.

6

Make it bite

Four chances to stop the same mistake. The earliest is the cheapest.

WhenWhat happensCost
Prompt submittedthe blocking rules enter the agent's context~40ms
Before a writea spec outside src/tests/ is denied~30ms
After a writeerror blocks the edit, findings go back to the model~140ms
Before a commitgate + ESLint on staged files~3s
Pull requestchanged files, budgets, one sticky comment~1min

A Claude Code hook reads JSON on stdin and answers with an exit code. 0 lets the action through; 2 blocks it and hands stderr back to the model to act on.

what the model receives, exit code 2
Quality gate blocked this edit to src/tests/demo.spec.ts:

src/tests/demo.spec.ts:1  [error] framework/spec-imports-playwright-test
    fix: Import from `@fixtures/test-base`.
src/tests/demo.spec.ts:14 [error] slop/test-without-assertion
    fix: Add a web-first assertion for the outcome the test is named after.

Telling the model the rules costs a few hundred tokens. Blocking an edit and having it rewrite the file costs a whole turn. Inject first, block second. And inject only the rules that block, or you bury them.

ESLint is deliberately not in the edit hook: 2.2 seconds against the engine's 0.14, on every keystroke-sized change. It runs at commit and in CI, where two seconds is free.

Try it Wire the edit hook, then ask your agent to write a spec importing @playwright/test. Watch it correct itself without you saying anything.

7

Make it survive

Most gates are deleted, not outgrown. Three things stop that.

Read every finding of the first run

The first full run here produced 174 findings. That was three wrong rules, not 174 problems.

HitsRoot causeFix
67a reporter that renders emoji, flagged as slopexclude by name, reason in the rule
14every exported interface reported as deadcount value exports only
11the best comments in the repo flagged as narrationmake the comment the denominator
5the logging wrapper told to stop loggingscope the rule to specs and page objects

Down to 73, all real. Only the first is an exclusion. Prefer narrowing a rule's scope: an exclusion says "not here", a scope says "here is where the premise holds".

Let people out, but never silently

A waiver with no reason is itself an error. A gate that can be switched off silently stops being a gate, and the reason is what a reviewer reads six months later. Waived findings still appear in the report, under their reasons.

Switch it on for changed files only

A gate turned on across a suite that predates it fails immediately, and the first response is always to weaken the gate. Scope CI to the diff and write the baseline down instead of sweeping it.

CheckErrorsWarnings
gate --all757
eslint src1321
tsc --noEmit00

So the whole repo does not pass today. That is the honest state, not a bug. What matters is that a pull request cannot add to either number.

Try it Set your CI budgets one below your worst branch, open a PR, watch it fail, then tune from evidence rather than a guess.

Now build it

The twelve-lesson version, and the exercises that mark your work.

CommandWhat it does
npm run gatewhole repo
npm run gate -- --file <path>one file
npm run gate:changedwhat this branch adds, with budgets
npm run gate:rulesevery rule and its severity
npm run exercisesmark the twelve lessons
node quality/selftest.mjsprove the rules still fire

The full twelve-lesson guide takes each step apart: the CLI and its four report formats, call sites and block bodies, the cross-file import graph, encoding your own non-negotiables, profiles and budgets, and the PR workflow.

The runnable half lives in exercises/. Four lessons are stubs checked against the real engine and the real import graph; the rest check the artifact each lesson adds. A clean clone reports 8 passing, 4 to do, 0 failing, and the to-dos are the point.
