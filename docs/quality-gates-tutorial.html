The spec that passes everything

Here is a Playwright spec. It compiles. ESLint has nothing to say about it. Run it and the suite goes green. Ship it and you have covered login.

Except it asserts nothing. It passes as long as no line throws, which means it reports green on a login page that is completely broken as long as the button is still there to click. And that is only the first of seven things wrong with it:

RuleWhat it caughtSeverity
slop/test-without-assertionThe test checks nothing. It cannot fail for the reason it exists.error
framework/spec-imports-playwright-testImports the raw test, so it gets none of the project's fixtures.error
framework/page-object-constructed-in-specnew LoginPage(page) bypasses the fixture layer.error
framework/locator-in-spec#login-button is invisible to every other spec.error
framework/credential-argument-literalThe test account is now hard-coded in a twelfth place.error
slop/generic-test-title"should work correctly" tells a failure report nothing.warn
slop/section-banner-comment// Arrange labels a shape everyone already recognises.warn
slop/narrating-comment// click the login button is the next line read aloud.warn

Nothing in a normal pipeline objects to any of this. A reviewer objects, once, and then gets tired. That is the gap generated code walks through, and it widens with the volume an agent can produce. This guide builds the thing that objects every time, in under a fifth of a second.

Two tools, one line between them

ESLint answers

  • Is this promise awaited?
  • Is this a hard wait?
  • Is this force: true?
  • Is this any?
  • Is this variable used?

Questions with one correct answer and, usually, a fixer.

vs

Only your repo answers

  • Is this helper used twice?
  • Does this comment add anything?
  • Does this spec go through the fixture?
  • Does the trace already record this?
  • Does anything import this export?

Questions that need the shape of this project.

One owner per rule. A hard wait is the most recognisable AI tell there is, and it will not appear in the ai-slop pack, because playwright/no-wait-for-timeout already owns it. Two tools reporting the same finding teaches people to skim past both.

Setup and project layout

The starting point is any Playwright + TypeScript suite. The examples come from AdvancePlaywrightFramework2x, which has page objects in src/pages/, fixtures in src/fixtures/, and specs in src/tests/. If your layout differs, the rules change; the engine does not.

Pin TypeScript to the major your tsconfig.json was written for. Installing typescript without a range pulled in 6.x during the original build and broke tsc --noEmit on two options that 5.x accepts happily: moduleResolution: node10 and baseUrl. A linter install should not force a compiler upgrade.

The engine half installs nothing. That is a decision, not a boast: it runs on every file the agent writes, so its start-up cost is the cost of the gate. Here is what you will have built by lesson twelve.

Every lesson adds one of those files and ends with a command you can run. Nothing is scaffolding you throw away later.

01

ESLint, the easy half

Flat config, type-aware rules, and the one rule that pays for the whole setup.

Start with the half that has correct answers. ESLint 9 uses a flat config: an array of blocks, each naming the files it applies to. Type-aware rules need projectService, which hands the parser your real tsconfig.json.

Run: npx eslint src playwright.config.ts

Output
src/tests/apisTests/01_restfulbooker_raw/01_basic_ping.spec.ts
  6:9  error  Unexpected console statement  no-console

src/tests/login/login.spec.ts
  18:57  error  'page' is defined but never used  @typescript-eslint/no-unused-vars

src/utils/SchemaValidator.ts
  33:23  error  This assertion is unnecessary since it does not change the type of the expression

no-floating-promises is the reason to accept type-aware linting. A missing await on a Playwright action does not throw. The test finishes early, passes, and the action lands on the next test's page. It is the only bug in this list that a green suite actively hides.

projectService

Gives rules the type checker, so they can tell a promise from a value. Costs about 2 seconds of start-up, which lesson 11 spends carefully.

flat/recommended

The Playwright plugin's own set: hard waits, force, focused tests, conditional expects. Scope it to src/tests/ so page objects are not judged as specs.

expect-expect: off

Turned off on purpose. Lesson 06 rebuilds it in a form that understands your assertLoaded() page methods.

Key takeaways

  • Flat config is an array of blocks, each scoped by files
  • Type-aware rules need projectService and a real tsconfig.json
  • no-floating-promises catches the bug a green suite hides
  • Scope the Playwright plugin to the spec directory only
  • Turn a plugin rule off when you intend to own that question yourself

Exercises

  1. Install the packages and add eslint.config.mjs. Run it over your src/ and write down the error count. That is your baseline.
  2. Delete an await in front of a page.click() and confirm ESLint reports it while the test still passes.
  3. Add playwright/no-skipped-test as a warning and see how many skipped tests your suite has been carrying.
  4. Run npx eslint --fix on a copy of your repo and count how many of the findings were mechanical.
02

The gap a linter cannot see

Why a second tool is needed, and the shape it has to take.

Run ESLint over the spec from the top of this guide and it finds one thing: an unused page parameter. Every genuine problem in that file, starting with the missing assertion, is invisible to it, and not because ESLint is weak. The questions are simply of a different kind.

"Does this spec go through the fixture layer?" has no universal answer. It depends on a fixture module that exists in this repo. A general-purpose linter cannot ship that rule, and you should not want it to.

Before any of that, write down what gets scanned and how hard each stage bites. Profiles are how one set of rules serves four stages: while the agent is writing code an error blocks the edit and a warning is advice; on a pull request the warnings are counted against a budget.

Budgets are per change, not per repo. A pull request may carry a handful of judgement-call warnings; it may not carry thirty. A per-repo budget would fail on day one and be deleted by day three.

Key takeaways

  • A general linter cannot hold rules that depend on your fixture module
  • One pipeline: lex, run rules, render, exit
  • Profiles let one rule set serve the edit loop, the commit, and the PR
  • Severity decides consequence, not importance
  • Budgets belong to a change, not to a repository

Exercises

  1. Write your own gate.config.mjs. Which directories in your repo are deliberately weird and should be excluded? Write the reason next to each one.
  2. List three questions your team asks in code review that no linter could answer. Those are your first rules.
  3. Decide your four profile names before writing any rule. What should block an agent mid-edit, and what should only ever be advice?
03

Reading source safely

The masked lexer. One technique separates a usable gate from a noisy one.

The naive version of this whole project is grep. It fails immediately, and always the same way:

A regex sees three hits. A reviewer sees one. The fix is to walk the file once and produce a second copy where comment bodies and string contents are blanked out, newlines preserved so every character still maps to its original line. Rules read that copy by default and opt into the comments or the strings when the prose is the point.

Here is a real page object, and the same lines after masking:

src/pages/LoginPage.ts, as written
    async open(): Promise<void> {
        this.log.info("Open login pgae");
        await this.goto(LoginPage.PATH);
    }
the same lines, masked
    async open(): Promise<void> {
        this.log.info("               ");
        await this.goto(LoginPage.PATH);
    }

Same length, same line numbers, same column positions. The string is gone and LoginPage.PATH is still there, because it is code. Every rule in the remaining nine lessons is built on that one property.

Masking has a cost, and lesson 07 pays it. The comment // click the login button sits above page.locator('#login-button').click(), and in the masked copy the words login-button are gone. A rule comparing the two has to read the raw line, not the masked one. Knowing which copy a rule needs is most of the skill here.

The same pass also collects what the file imports, exports, and declares. Lesson 08 turns that into a graph.

layer

Derived from the path. src/pages/ is a page, src/tests/ is a spec. Rules are scoped by layer, which is how one rule can apply to specs and not to helpers.

lineAt()

A regex match gives you an offset. Findings need a line. Pre-compute the line starts once, then binary search.

regexAllowedAt()

Twelve lines of care so a division sign is not mistaken for a regex literal, which would swallow the rest of the file as a string.

Key takeaways

  • Never regex raw source: a match in a comment is documentation, not a finding
  • Mask comment and string bodies, preserve every offset and newline
  • Record comments and strings separately so rules can opt in to them
  • Derive a layer from the path and scope rules by it
  • Collect imports and exports in the same pass; lesson 08 needs them

Exercises

  1. Write lex() and run it over your largest page object. Print the masked copy next to the original and check that no line number moved.
  2. Feed it a file containing const re = /\/\//; and a line with a division. If the rest of the file vanishes, your regex detection is wrong.
  3. Add a layerOf() that matches your directory names, and print the layer of every file in src/. Anything landing in other is a directory your rules will silently skip.
04

Your first rule

Rules are data, detectors are code. The split that keeps this maintainable.

The temptation is to write each rule as a function. Fifty rules later, adding "no page.pause() in specs" means writing code, testing code, and reviewing code, and nobody adds the rule.

Instead: a rule is a plain object naming a detector and its options. The detectors are code and there are twelve of them. Rules are data and there are forty-six.

why and fix are not documentation, they are the product. They print in the terminal, in the feedback the agent reads when its edit is blocked, and in the pull request comment. A rule whose why says "this is bad practice" gets waived by the first person who hits it.

The regex detector is the workhorse. Note the target: this is where lesson 03 pays off.

The runner loads every *.rules.mjs pack, decides which files each rule applies to, and calls the named detector.

A bug worth stealing. The glob translator in matchesAny converted ? to . as its last step, after it had already produced (?:.*/)? groups, so it rewrote its own output. Every pattern matched nothing, the walker found one file, and the gate cheerfully reported a clean repo. Substitute the wildcards before you create any regex syntax of your own, and always check the file count.

Key takeaways

  • Detectors are code, rules are data: adding a rule is a four-line data change
  • Every rule names a detector; an unknown name is a hard error, not a silent skip
  • target chooses masked code, raw text, comments, or strings
  • why and fix are what the reader acts on, so write them like it
  • A gate that reports zero findings is a gate you should distrust until you prove it scanned something

Exercises

  1. Add slop/constant-assertion and run it over a file where you have pasted expect(true).toBe(true). Then put the same text in a comment and confirm it is not reported.
  2. Write slop/no-page-pause for page.pause(), specs only. It should be four lines plus a why and a fix.
  3. Write the why for your rule twice: once as "this is bad practice", once naming what breaks. Show both to a colleague and ask which one they would act on.
  4. Deliberately typo a detect value and confirm your runner throws rather than skipping the rule.
05

The report and the CLI

Four renderings of one set of findings, and the exit code that makes them bite.

Four stages consume this gate and each wants a different shape. All four call one CLI, which is the only way the pull request comment can never disagree with your terminal.

FormatWho reads itShape
consoleyou, in a terminalgrouped by file, coloured, why and fix on first occurrence of each rule
hookthe coding agentno colour, no prose, one line per finding plus the fix
markdownthe pull requesta per-gate table, collapsible sections, budget breaches
jsonanything elseeverything, for your own tooling

One detail matters more than it looks: why and fix print on the first occurrence of a rule and are omitted on repeats. Eleven copies of the same two paragraphs is how a report teaches people to skim past it.

The CLI decides what to report on. The scan itself is always the whole repo, which lesson 08 explains; only the report is scoped.

Key takeaways

  • One CLI serves every stage, so no two reports can disagree
  • Print why and fix once per rule, not once per finding
  • Scope the report, not the scan

  • Separate "the gate failed" from "the gate crashed" in the exit code

Exercises

  1. Add --format json and pipe it into a one-line script that counts findings per rule. You will use it constantly in lesson 12.
  2. Run the gate on a branch where you only changed the README. It must report nothing and exit 0.
  3. Break your engine on purpose (throw inside a detector) and confirm the CLI exits 2 with a stack trace rather than exiting 1 with a clean report.
06

The ai-slop pack

Tests that assert nothing, and the difference between a silent catch and a documented one.

Regex gets you a long way, but not to the most valuable rule in the whole system: does this test assert anything? That needs the body of a test() call, and finding it is fiddlier than it looks.

Brace counting is only safe because it runs on the masked copy: no braces from strings, comments or template interpolation survive into it. With call sites in hand, the rule is small.

Why this beats playwright/expect-expect, which we turned off in lesson 01. The required pattern also accepts a page-object method named assertLoaded(). In a framework where assertions legitimately live inside the page object, a rule that only knows expect reports false positives on your best-written specs.

The empty catch, and a lesson about which copy to read

An empty catch turns a red test green. In a suite whose entire job is finding failures, it is the worst line available. The obvious rule:

Masking blanks the comment body, so the block looks empty. But a catch that explains itself is the thing we want people to write. Switching the rule to the raw text fixes it, because the comment characters are still there:

slop/constant-assertionexpect(true).toBe(true)error
slop/swallowed-errora genuinely empty catcherror
slop/not-implementedthrow new Error('Not implemented') that reached reviewerror

slop/section-banner-comment// Arrange, // Act, // Step 1warn

Key takeaways

  • The most valuable rule needs a block, not a line: find call sites and their bodies
  • Locate the callback arrow at argument depth, or a destructured parameter list becomes the body
  • Brace counting is only safe on the masked copy
  • Accept the project’s own assertion idioms, not just expect
  • A catch that explains itself is documentation; match raw text so the comment saves it

Exercises

  1. Implement callSites and print every test name in your largest spec with its statement count. Any test whose body is null means your arrow detection is wrong.
  2. Add slop/test-without-assertion and run it over your whole suite. Every hit is a test that is currently reporting green on something it never checks.
  3. Extend required with your own project’s assertion helpers, then re-run and watch the false positives disappear.
  4. Write the empty-catch rule against masked code first, find a documented catch in your repo, then switch it to raw and watch the finding go away.

The ponytail gate

Cutting what the run already records, and the metric that was wrong the first time.

This framework carries two copies of the same API lifecycle test on purpose. booking-crud.e2e.spec.ts is 73 lines. booking-crud-end-to-end.ponytail.spec.ts covers the same create, update, read-back and delete in 33. Same assertions, both green. The README keeps both so the diff is readable.

Every cut answered one question: does anything else in the run already record this?

CutWhat already records it
test.step around a single callThe trace lists every request, with timings
testInfo.attach of a response bodyThe same trace already holds it
Ten log.info linesEach restated its own step name, which is in the HTML report
Date.now() timingThe trace timeline has every duration
An explicit token argumentOmitting it routes through the path that re-auths on a 403

The precondition this gate rests on. All of it depends on playwright.config.ts setting trace: 'on' for every test, not just retries. Turn tracing off and the attachments stop being redundant, and this entire pack should be turned off with it.

Exercises

  4. Check your playwright.config.ts. If trace is on-first-retry, write down which rules in this pack you must disable and why.

Seeing across files

The import graph, and why one-file scanning cannot find over-engineering.

"Does anything import this export?" cannot be answered from inside the file that defines it. Neither can "how many callers does this helper have?". Those two questions are most of what over-engineering actually is, so the engine builds a graph of the whole repo before any rule runs.

Aliases come from tsconfig.json rather than being hard-coded, so the graph cannot drift from what the compiler resolves.

One trap is worth knowing before it bites you. A module can be in use without any file importing it:

That reporter is very much in use, and a naive "unused export" rule reports it. The index therefore also collects paths named inside string literals:

With the graph in place the over-engineering rules are almost declarative.

That kinds filter removed 14 of 20 findings. Before it, every exported interface in the repo was reported. The rule was not detecting over-engineering; it was detecting TypeScript.

What this pack deliberately does not flag. UtilElementLocator is a wrapper whose job is to log every action, and BasePage is one base class one level deep. Both look like indirection and neither is: over-engineering is an abstraction with no consumer, not an abstraction you personally would not have written. Write that distinction into the pack’s header comment, because someone will argue about it.

Key takeaways

  • Build the import graph before any rule runs; scope the report, never the scan
  • Read path aliases from tsconfig.json so the graph matches the compiler
  • A module named in a string literal is still in use
  • Exclude type exports, or the rule just detects TypeScript
  • Name the abstractions that are intentional, in the pack, before someone simplifies them

Exercises

  1. Build the index and print every export in src/utils/ with its importer count. The zeros are your dead surface.
  2. Add the stringRefs pass. Remove it again and watch your custom reporter get reported as unused.
  3. Implement singleConsumer for modules over 25 lines with exactly one importer. Move one of them next to its caller and see whether anything got worse.
  4. Write the "intentional abstractions" note for your own repo. Which two files would a stranger wrongly simplify?
09

Your non-negotiables

Turning the conventions document nobody enforces into rules that bite.

Most teams already have this document. In this repo it is .github/copilot-instructions.md, and it opens with nine numbered non-negotiables: specs import from the fixture module, never construct a page object, never hold a locator, and so on. It was accurate, well written, and had no way at all to notice when something ignored it.

Every rule in this pack carries an nn field naming the item it enforces. A finding then traces back to a sentence instead of to an opinion, which is the difference between a rule you can defend in review and one you cannot.

The best why in the whole system is that one, because it names a bug the team actually had. Go through your own incident history before writing this pack. A rule that prevents a failure someone remembers never gets argued with.

Two detectors carry most of this pack. importShape answers "may this layer import that?", and fileMissing answers "does this file never do something it must?".

The exclusions matter as much as the rules. This repo teaches the raw request fixture in apisTests/01_restfulbooker_raw/, so forcing those specs through a UI fixture would destroy the lesson they exist to teach:

State an exclusion in the rule, never in a reviewer’s head. An exclusion that lives only in someone’s memory becomes an argument the first time a newcomer trips over the rule.

RuleNNWhat actually breaks
framework/spec-imports-playwright-test1The spec gets none of the fixtures. It has silently left the framework.
framework/page-object-constructed-in-spec2Built against a different lifecycle; setup gets repeated by hand.
framework/locator-in-spec3Invisible to every other spec. You fix the page object and this still fails.
framework/page-object-not-extending-base4No action logging, and goto stops respecting baseURL.
framework/dotenv-in-spec5Hoisted imports read process.env before .env loads.
framework/inline-credential-literal6A credential in the source is a credential in the git history.
framework/zod-import7Not a dependency. Does not install in CI.
framework/cross-layer-relative-import10../../../api/X breaks the moment either file moves.

Key takeaways

  • Your conventions document is a rule pack that was never executable
  • Tag each rule with the numbered item it enforces
  • Write why from a real incident wherever you can
  • importShape and fileMissing cover most framework rules
  • Every deliberate exclusion belongs in the rule, with its reason

Exercises

  1. Open your team’s conventions doc and number the rules. How many could be a regex over imports? Write those three first.
  2. Find a bug your team actually shipped that a convention would have prevented. Write that rule and put the incident in its why.
  3. Add framework/cross-layer-relative-import and run it over your repo. Every hit is a file that cannot move without breaking an importer.
  4. For each exclusion you add, write one sentence explaining it. If you cannot, the exclusion is probably a rule that is wrong.
10

Waivers and budgets

Every gate needs an escape hatch. The trick is making it cost something.

A gate with no escape hatch gets deleted the first time it is wrong. A gate with a free escape hatch gets switched off everywhere and stops existing. The design goal is an exit that is always available and never silent.

The rule about the rules: a waiver with no reason is itself an error. The runner emits it as a finding, from the engine rather than from any pack.

Waived findings are still listed in the report, under their reasons, instead of disappearing. Suppression you cannot see is indistinguishable from a rule that never ran.

Budgets

Errors block. Warnings are judgement calls, and the honest position on a judgement call is that a few are fine and thirty are not. That is a budget, counted per change:

Output
Quality Gate - ci profile - 2 changed files checked - 4 error, 14 warn

  ai-slop              1 error, 5 warn, 0 info
  framework-patterns   3 error, 0 warn, 0 info
  ponytail             0 error, 9 warn, 0 info

  budget: ponytail allows 8 warn per change, found 9

gate failed
error

Blocks an agent edit, a commit and the pull request. Thirteen rules out of forty-six.

warn

A judgement call. Printed everywhere, counted against the per-change budget on the PR.

info

A prompt to look. Never blocks anything, ever.

Key takeaways

  • Always provide an escape hatch, and never let it be silent
  • A waiver without a reason is an error in its own right
  • List waived findings with their reasons instead of hiding them
  • Budget warnings per change, not per repository
  • Thirteen blocking rules out of forty-six is a workable ratio; start lower

Exercises

  1. Implement waivers with the reason requirement. Add a bare // gate-allow and confirm the gate reports it as an error.
  2. Add a real waiver to a real finding in your repo. Read the reason you wrote. Would it convince you in six months?
  3. Set your ci budgets one below your current worst branch, then open a PR and watch it fail. Tune from evidence, not from a guess.
  4. Make gate-allow-file work for the whole file and decide, in writing, which rules may never be waived file-wide.
11

Pre-generation hooks

Where this stops being a linter and starts shaping the code as it is written.

Everything so far reports on code that already exists. The interesting move is to put the gate inside the loop that writes it. Claude Code fires hooks around its own tool calls, each reading one JSON object on stdin and answering with an exit code: 0 lets the action through, 2 blocks it and hands stderr back to the model as feedback to act on.

The cheapest hook is the first. Telling the model the rules before it writes costs a few hundred tokens; letting it generate a spec, blocking the edit, and having it rewrite the file costs a whole turn.

The hook that runs after every write is the one that changes behaviour. It scopes the report to the single file and blocks only on errors, so contract breaks are fixed immediately while the judgement calls are shown as advice.

    fix: Move it into the matching `src/pages/*.ts` as a `private readonly` field.

ESLint is deliberately absent from this hook. A type-aware lint of one file costs about 2.2 seconds; the engine costs 0.14. Paying two seconds on every edit buys nothing the engine has not already caught, so ESLint runs at commit time and in CI, where two seconds is free. Measure both before you decide; the obvious version of this system runs everything everywhere and is abandoned in a week.

The PreToolUse guard on Write handles the one thing that cannot be fixed by editing the file afterwards: its location. A spec written next to a page object runs under the wrong Playwright project, against the wrong baseURL, or is never collected at all. That is a hard deny with a reason, and it is kept to rules with no judgement in them.

Key takeaways

  • A hook reads JSON on stdin and answers with an exit code; 2 blocks and feeds stderr back
  • The cheapest gate is the one that runs before generation, not after
  • Inject only the blocking rules, or you bury them
  • Block on errors, print warnings: fix contract breaks now, show taste findings as advice
  • A gate that crashes must let the work through, never block on its own bug
  • Enforce file placement before the write; everything else can be fixed after

Exercises

  1. Wire gate-on-edit.mjs and ask your agent to write a spec that imports @playwright/test directly. Watch it correct itself without you saying anything.
  2. Time both tools on one file: time npx eslint <file> against time node quality/gate.mjs --file <file>. Decide from your own numbers which belongs in the edit loop.
  3. Break your engine on purpose and confirm the hook exits 0 with a message rather than blocking every edit in the session.
  4. Add the .githooks/pre-commit script and git config core.hooksPath .githooks. Try to commit a spec with no assertion.
12

The PR gate, and shipping it

Calibration, a selftest, and how to switch this on without everyone hating you.

The workflow scopes to changed files, posts one comment it edits in place, and fails the build on an error or a budget breach. Two steps in it are easy to skip and both matter.

The comment is found by a marker in its own body and updated rather than appended. A gate that posts a new comment on every push trains people to collapse the thread.

Calibration: the part that decides whether this survives

The first full run over this repository produced 174 findings. Reading all of them found three rules that were wrong, not a hundred and seventy-four problems.

SymptomRoot causeFix
67Emoji findings, all in one file: a reporter that renders a console and HTML reportExcluded by name, with the reason in the rule
14Every exported interface reported as unused surfaceRestrict the rule to value exports
11Explanatory comments flagged as narration, including the best one in the repoMake the comment the denominator
5The logging wrapper told to stop loggingScope the rule to the layers the trace covers

That took it to 73, which were read individually and are real.

Prefer narrowing a rule’s scope over adding an exclusion. An exclusion says "not here". A scope says "here is where the premise holds". The ponytail fix was the better one for exactly this reason: the trace does not record what a helper does internally, so the rule never belonged in the util layer at all.

A gate with no test of its own

...is the thing these rules exist to catch. Two fixtures: one written the way a model writes a spec when nobody is watching, one written the way the framework documents. The first must produce a named list of findings; the second must produce none.

The fixtures are .txt on purpose, so neither tsc nor ESLint tries to compile deliberately broken code. They are read with a pretend repo-relative path, and that path is what decides their layer.

Switching it on

A gate switched on across a suite that predates it fails immediately, and the first response is always to weaken the gate. Introduce it on changed files only, and write the baseline down so it is paid off deliberately rather than discovered:

CheckErrorsWarningsNote
gate --all757every one read by hand during calibration
eslint src13219 auto-fixable with --fix
tsc --noEmit00clean

So npm run lint and npm run gate do not pass on the whole repository, and that is the honest state rather than a bug. What matters is that a pull request cannot add to either number. Pay it down file by file as you touch them; a sweep that reformats forty files to get one number to zero is a review problem, not an improvement.

Key takeaways

  • Scope CI to changed files, or the gate fails on day one and is deleted by day three
  • Run the selftest in CI before trusting the gate’s verdict
  • One pull request comment, edited in place
  • Read every finding of the first full run; a rule firing 67 times has found a class it does not understand
  • Scope beats exclusion
  • Write the baseline down instead of sweeping it

Exercises

  1. Run your gate over your whole repo and read every finding. Group them by rule and fix the rules, not the code.
  2. Build the two fixtures and the selftest. Add one rule id at a time until every rule you own is covered.
  3. Add the workflow and open a deliberately bad pull request. The comment should tell you what to do without opening the job log.
  4. Write your adoption baseline into your README. Three numbers and one sentence about who pays them down.
  5. Six weeks later: which rule has been waived the most? Either its why is weak or the rule is wrong. Fix whichever it is.

What comes next

Forty-six rules, four gates, four firing points, and a selftest. The parts worth extending, roughly in order of value:

Package the judgement, not just the rules

A rule says a comment restates the code. It cannot say what the gate cannot see: assertions that cannot fail, a title and body that disagree, coverage theatre. That belongs in a skill your agent loads by task, next to the rule pack.

Rules from your own incidents

The strongest rule in this system names a bug the team actually had. Read your last ten postmortems and write one rule per preventable one.

Track waivers over time

The most-waived rule is either badly explained or wrong. A weekly count tells you which rules are earning their place.

Extend the detectors, carefully

Twelve detectors cover forty-six rules. Before writing a thirteenth, check the idea really cannot be expressed with the ones you have.
