Lint Before You Push

What a type check, a linter and a quality gate each catch, how to add all three to a Playwright project, and how to make them run before your code leaves your machine.

  • 8 steps
  • about 40 minutes
  • no prior ESLint knowledge
  • TypeScript + Playwright

By Pramod Dutta, founder of The Testing Academy

1

Three checks, three jobs

They sound similar and they overlap almost not at all.

CheckThe question it asksCommand
Type checkDo these values and calls actually fit together?tsc --noEmit
LintIs this code using the language and the library in a known-bad way?eslint
Quality gateDoes this fit the shape of our project?node quality/gate.mjs

That sounds abstract until you watch them miss each other. Here is one spec. The type checker finds two problems:

npx tsc --noEmit
src/tests/demo/demo.spec.ts(4,40): error TS2345: Argument of type 'number' is not assignable to parameter of type 'string'.
src/tests/demo/demo.spec.ts(6,27): error TS2339: Property 'itemRow' does not exist on type 'CartPage'.
npx eslint on the same file
(no output)

ESLint has nothing to say, and it is not being lazy. It does not know what a CartPage is or what addToCart expects. Now the reverse. A different spec, all types correct:

npx tsc --noEmit
(no output)
npx eslint
4:11  error    'unused' is assigned a value but never used             @typescript-eslint/no-unused-vars
5:5   error    Promises must be awaited, end with a call to .catch ...  @typescript-eslint/no-floating-promises
6:11  error    Unexpected use of page.waitForTimeout()                  playwright/no-wait-for-timeout
9:11  warning  Prefer locator methods instead of page methods           playwright/prefer-locator
9:50  error    Unexpected use of { force: true } option                 playwright/no-force-option

5 problems (4 errors, 1 warning)

Line 5 is the one to fear. addToCart is never awaited, so the test does not wait for it. It finishes early, passes, and the click lands on the next test's page. A green suite hides that. Only the linter sees it, and only because it can read types.

Try it Run npx tsc --noEmit on your project right now. Whatever it prints is code that is already wrong.

2

What a linter actually does

It is less magic than it looks: parse, walk, report.

ESLint reads your file and turns it into a tree. await page.click() becomes an AwaitExpression containing a CallExpression whose callee is a MemberExpression. Each rule is a small program that says "when you walk past a node shaped like this, report it".

That is the whole idea. Everything else is configuration.

TermWhat it means in practice
ruleone check, with a name like no-unused-vars
severity"off", "warn" (prints, exit 0), "error" (prints, exit 1)
plugina package of extra rules, e.g. eslint-plugin-playwright
configwhich rules run, at what severity, over which files
fixablea rule that can rewrite the code itself, with --fix
type-awarea rule that asks the TypeScript compiler about types. Slower, and much smarter

Only error fails a build. A warning is a note that prints and exits 0, which makes it the right severity for "we would like to, eventually".

a real run, fixable problems
--- before ---
4 problems (1 error, 3 warnings)
  1 error and 3 warnings potentially fixable with the `--fix` option.

--- after npx eslint --fix ---
(no output)

Run --fix first, always. Formatting, spacing and import order are mechanical. Spend your attention on what is left after the machine has taken its share.

Try it Run npx eslint src --fix on a scratch branch and look at the diff. Everything in it is work you never have to do by hand again.

3

Add the type check

Five minutes, one flag, and it is the cheapest of the three.

Playwright compiles TypeScript on the fly, so a suite can run for months with type errors in it. tsc --noEmit is how you find out. --noEmit means "check, but write no JavaScript": you only want the errors.

Two settings in tsconfig.json do most of the work:

Pin your TypeScript version to the major your config was written for. Installing typescript unpinned here pulled in 6.x and broke tsc --noEmit on two options 5.x accepts happily, moduleResolution: node10 and baseUrl. Nothing in the project had changed. Use "typescript": "^5.9" and upgrade deliberately.

Try it Add the script, run it, and fix whatever it finds before going further. Step 4 is easier on a project that type checks.

4

Add ESLint

One config file, four blocks, each scoped to the files it judges.

ESLint 9 uses flat config: a file called eslint.config.mjs exporting an array. Each entry says which files it applies to and what rules they get. Later entries win. That is the entire mental model.

projectService: true is the line that pays for everything. Without it ESLint only sees text, and no-floating-promises cannot exist. With it, a rule can ask "is this expression a Promise?" It costs about two seconds of start-up, which step 8 spends carefully.

Try it Run npm run lint. Write down the number. On an existing project it will not be zero, and step 8 explains why that is fine.

5

Rules: on, off, and down

Four ways to change a rule, in order of how much you should reach for them.

1. Set its severity

2. Scope it to a folder

The honest fix when a rule is right almost everywhere. Add a later block for the exception and say why in a comment:

3. Disable one line, with a reason

The text after -- is the description, and ESLint keeps it. A bare eslint-disable-next-line is a silent opt-out, which is the same problem as a waiver with no reason. You can even require the description:

4. Disable a whole file

Almost never. If a file needs this, it usually needs a scoped block in the config instead, where the reason is visible to everyone rather than buried at the top of one file.

Reach downward, not sideways. Severity first, then scope, then one line with a reason. Every step down the list hides the exception from more people.

Try it Find the noisiest rule in your run. Decide, out loud, whether it is wrong everywhere (severity), wrong in one folder (scope), or wrong once (a line comment).

6

The rules that matter for test code

A general linter does not know what a flaky test looks like. This plugin does.

RuleWhat it prevents
@typescript-eslint/no-floating-promisesA missing await. The test finishes early, passes, and the action lands on the next test's page.
playwright/no-wait-for-timeoutwaitForTimeout(3000). Slow when it works, flaky when the app is slower than your guess.
playwright/no-force-option{ force: true } clicks an element the user could not have clicked. The bug ships.
playwright/prefer-web-first-assertionsexpect(await el.textContent()), which reads once instead of retrying.
playwright/no-conditional-in-testAn if in a test: half the time it checks nothing and still reports green.
playwright/no-focused-testtest.only reaching CI, where it silently skips the rest of the file.
playwright/no-element-handle$() handles, which go stale on re-render. Locators re-resolve.
playwright/valid-expectexpect(locator) with no matcher. Asserts nothing at all.

Two before-and-afters worth internalising:

Scope the plugin to your spec folder. A page object legitimately holds locators and helper methods; judged as a spec it fails rules that were never about it.

Try it Turn on the eight rules above, run npm run lint, and read the hits in your oldest spec file. That is your flakiness backlog, itemised.

7

Write your own rule without writing a plugin

Most team conventions are one selector away.

You do not need to publish a package to enforce a house rule. no-restricted-syntax takes an AST selector, which reads like CSS for code:

npx eslint on a spec containing test.only
3:1  error  test.only silently skips the rest of the file. Delete it before pushing.  no-restricted-syntax

To find the selector for something, paste the code into astexplorer.net, pick the TypeScript ESLint parser, and click the node you want. The panel names its type and properties.

Where this runs out. A selector matches shapes, not meaning. "Does this test assert anything?", "does this comment add anything?", "does anything import this?" need a body, a word count, or the whole repo. That is the point where a separate rule engine earns its place, which is what the quality gates guide builds.

Try it Write one selector rule for the mistake your team corrects most often in review. You now never have to write that comment again.

8

Run it before you push

A check nobody runs is a check you do not have.

Four places to run these, and they are not interchangeable. Cost decides which goes where.

WhereRunsScopeCost
On save, in your editorESLintthe open fileinstant
pre-commitlint + gatestaged files~3s, many times a day
pre-pushtypecheck + lint + gatethe whole branch~8s, a few times a day
CI, on the pull requesteverythingthe diff against main~1min, once per push

A type check is a whole-project operation, so it belongs at push rather than in front of every commit. Nobody accepts an eight-second pause fifty times a day, and a hook people bypass is worse than no hook.

Wire the hooks, without a dependency

Git looks for hooks in .git/hooks, which is not committed. One config setting points it at a folder that is:

git push, on a branch that is in good shape
pre-push: type checking the project...
pre-push: linting changed files...
lint: 3 changed file(s) clean
pre-push: quality gate on the branch...
Quality Gate - ci profile - 3 changed files checked - no findings
pre-push: clean

The mistake that kills hooks

Never lint the whole repo in a hook on an existing project. Turn these on over a suite that predates them and the first run is red through no fault of the person pushing. They add --no-verify once, it becomes muscle memory, and the hook is now decoration. Scope every hook to the diff and let the baseline be paid down deliberately.

Here that baseline is 13 ESLint errors and 21 warnings, all pre-existing, written down in the README so nobody discovers it by surprise. A pull request cannot add to it, which is the property that actually matters.

The scripts

verify is the audit and it does not pass today. verify:branch is the gate and it must. Keeping both, and being honest about which is which, is what stops the audit number from being quietly deleted.

And always leave the escape hatch. git push --no-verify skips the hook. Someone with a real reason will find a way around it regardless, and a bypass that is visible in the command they typed is better than one that is not.

Try it Enable the hooks, then push a branch with a missing await in it. The push should stop before the network call.

What this does not cover

The checks that need to know your project, not just your language.

Everything above is generic: any TypeScript project can use it unchanged. What none of it can answer is whether a test asserts anything, whether a comment adds anything, whether a helper has more than one caller, or whether a spec goes through your fixture layer. Those need a tool that knows your repository.
